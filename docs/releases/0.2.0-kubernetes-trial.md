## 隔离边界

- 应用 Secret、Helm 和 Pod 操作使用 `system:serviceaccount:artifactory:artifactory-deployer`。再次实测它不能修改 `default` 的 Deployment、创建 CRD 或修改节点。
- 没有安装 Operator / CRD、创建 ClusterRole / PriorityClass、配置公网入口，或修改节点 DNS、containerd、CNI、StorageClass 及其他命名空间的工作负载。
- 配额限制 requests 为 4 CPU / 6 GiB、limits 为 12 CPU / 12 GiB、PVC 申请为 40 GiB。现场只读检查中，五个工作节点的 imagefs 均有超过 80% 可用空间。
- 新 Pod 使用默认优先级 0。安装前确认没有默认高优先级类、现有非目标 Pod 最低优先级为 0；新 Pod 无法抢占这些现有工作负载。
- 14:20 CST 对 139 项非目标 Deployment、StatefulSet、DaemonSet、Service、Ingress、NetworkPolicy、PVC、配额和 RBAC 等对象的 UID 与选定规格摘要复核：138 项不变，1 项检测到同期外部 Helm 更新。该对象不在本次操作范围，受限部署身份无权修改，也没有对它执行回滚或修复。不能把这个结果描述成所有外部资源均未变化。
- 上述摘要不覆盖全部集群对象或运行状态；已有 provisioner 为本项目 PVC 正常创建的 PV、应用镜像缓存和状态更新是预期部署行为。详细命名、主机和审计记录只保存在本机私有目录，不公开到仓库。

## 本次兼容处理

1. 目标集群的 Priority admission 拒绝不匹配 PriorityClass 的逐 Pod `preemptionPolicy: Never`。原始 0.2.0 包保持不变，通过版本化 overlay 清空该值；当前源码 profile 已移除错误设置，不创建集群级 PriorityClass 绕过限制。
2. 节点直连 Docker Hub / GHCR 超时，初始依赖镜像传输端点的部分 blob 也无法访问。为三个固定依赖复制完整、摘要不变的项目缓存，并通过已核对摘要的南大端点拉取；没有改变节点或全局网络配置。
3. 第一次安装因拉取耗时触及 15 分钟超时，Helm `--atomic` 自动卸载应用，保留 PVC 和外部 Secret。镜像缓存完成后，使用原始发布包和最终 overlay 重新安装成功。
4. 已发布包的 NOTES 仍有历史单副本及固定 PVC 数量提示；以 Chart 的 Source 隔离约束、现场验证及本文为准。当前 `main` 已修正文案，未为了修改提示而重写发布包。
5. 原始源码标签的 Emissary Dockerfile 遗留默认构建版本 `0.1.0`。发布流程显式传入 `ARTIFACTORY_BUILD_VERSION=0.2.0` 和上述 `ARTIFACTORY_BUILD_COMMIT`，并已执行容器确认实际版本；手工从原标签构建也必须传入这两个参数。当前 `main` 已同步默认值，并把该字段加入版本漂移检测。

## 可复现配置

统一版本和凭据初始化见[统一版本与发布](../versioning.md)。先下载并核对发布资产，再提取原始 profile：

```sh
tar -xOf .local/release/artifactory-0.2.0.tgz artifactory/values-trial.yaml \
  > .local/release/values-trial-0.2.0.yaml
helm upgrade --install artifactory .local/release/artifactory-0.2.0.tgz \
  --kubeconfig "$PRIVATE_KUBECONFIG" --namespace artifactory \
  --kube-as-user system:serviceaccount:artifactory:artifactory-deployer \
  -f .local/release/values-trial-0.2.0.yaml \
  -f deploy/releases/0.2.0-trial-values.yaml \
  --atomic --wait --timeout 15m
```

`deploy/releases/0.2.0-trial-values.yaml` 是不含凭据的历史镜像与兼容配置快照；使用时仍需重新检查权限、优先级、容量、镜像端点与 CNI。控制台仅通过本机 `127.0.0.1:38100` 转发访问，S3 签名地址端口为 `38333`。

## 未通过或未覆盖

- 完整 `platform-contracts` CI 没有全绿：`linux-end-to-end` 的 SSH refs fixture 被 OpenSSH 以 `/tmp` 目录 ownership / modes 不合要求拒绝，得到 502 而不是预期 200；`kubernetes-pi` 在 kind 初始化时遭遇 kubeadm 1.36 拒绝 `v1beta3` 配置。没有将这两项失败冒称为通过，也未在本次受限部署中扩展修复范围。
- 该源码 CI 的版本契约、Compose TLS 和六平台 native-emissary job 通过；它们不等同于签名发行、实体设备或生产验收。
- PostgreSQL、S3、Source、Telemetry 和 Agent worker 均为单副本，不是全栈 HA；没有做节点故障注入、10k 负载、真实模型调用、私有 Git、设备构建、制品上传下载及恢复演练。
- HTTP 仅用于明确批准的内网试验。正式上线仍需可信 HTTPS、备份 / 恢复、外部高可用数据服务及完整流水线验收。
