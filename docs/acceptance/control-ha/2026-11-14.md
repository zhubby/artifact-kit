# Control 多副本与设备连接验收（SQLx 阶段归档）

日期：2026-11-14，Asia/Shanghai。工作区 `codex/control-ha`，基线 `c474b33`。
本记录对应合并 Toasty 之前的实现与隔离测试，没有部署或迁移已有安装。合并后的验证另见 [Toasty 整合验收](2026-11-14-toasty.md)。

## 实现范围

PostgreSQL 持久命令 Outbox、NOTIFY 唤醒与定时补偿；按 job 的有界调度、
跨副本 slots 锁与会话 fencing；事务外制品校验及并发限额；复用独立日志
mTLS 通道；设备分页与有界规划摘要；独立 legacy Source 与 Control emptyDir；
SIGTERM readiness 排空、连接预算和 Helm HA overlay。没有新增消息中间件。
部署与回退步骤见 [多副本指南](../../control-ha.md)。

## 设备压测方法

`tests/control/load.py` 在专用 TimescaleDB 中创建随机 schema，启动三个实际
Control 子进程；每台虚拟设备使用独立证书与实际
mTLS 双向流。数据库为 PostgreSQL 17.11 / TimescaleDB 2.32.0，保留默认 fsync 与同步提交。镜像为 `docker.m.daocloud.io/timescale/timescaledb:2.32.0-pg17`（仓库摘要 `6a6b7d7a346d7c6be03a310c240706f3bbc6d7adbdf3fbc07823570b34337f5e`）。先建立全部连接并等待指定数量的 running attempts，再按
10 秒周期发送心跳。测量窗口为 60 秒，在约 20 秒处 SIGKILL 副本 0，
约 40 秒处 SIGTERM 副本 2；设备集中重连到副本 1。测试中的 drain 为
1 秒，生产默认 5 秒；连接恢复预算保持 20 秒。

通过条件保持为：心跳 P99 < 2,000 ms、API P95 < 1,000 ms，至少两轮全量
心跳样本、API 全成功、设备全恢复、attempt ID 不变、全部 running leases
有效且没有最终设备错误；恢复预算内的可重试 RPC 错误单独计数。API 同时探测 overview 和 100 条设备列表。故障阶段、
恢复等待和启动阶段分别保留延迟样本；数据库探测每 500 ms 独立运行。

早期档位每进程连接池为 20，专用数据库上限为 100。HA 预算验证改为每进程
40，专用数据库上限为 200；仅修改连接预算，fsync、同步提交、延迟与恢复
门槛均保持不变。每档配置在结果中明确标注，新增证据 JSON 同时记录服务器
版本、连接上限、持久化设置及每进程连接数。HA overlay 为 Control / Source
配置 40；滚动重叠时业务与遥测预算合计最多 360，示例库预留 450。

虚拟执行器接受任务并续租，不运行真实编译；受控 S3 peer 只处理初始化。
本项不证明制品吞吐、遥测采集吞吐、SSE 浏览规模、真实 Kubernetes 滚动
升级或 Windows/Linux 设备安装。主机为共享 macOS 开发环境，Apple M1 Max、
10 个逻辑 CPU、32 GiB 内存。测试容器未设置独立内存限制，Docker VM 可用
内存约 15.66 GiB；万台档数据库 `shared_buffers=4009MB`、`wal_buffers=16MB`、
`max_connections=200`，`fsync`、`synchronous_commit`、`full_page_writes`
均为 on。本次不能证明 Helm 示例的数据库 4 GiB 内存限制可承载相同负载。
RSS/CPU 是幸存进程的单次快照，不能解释为生产峰值预算或生产 SLO。

复现命令（数据库 URL 由私有环境注入）：

```sh
export ARTIFACTORY_TEST_DATABASE_URL='<disposable TimescaleDB URL>'
python3 tests/control/load.py --release \
  --cargo-config 'profile.release.build-override.strip="none"' \
  --nodes 10000 --active 1000 --seconds 60 --database-connections 40
```

本机默认 release 构建的 SQLx 过程宏加载报 `mis-aligned LINKEDIT string pool`；
定向清理后重建仍可复现。上述覆盖仅关闭构建工具/过程宏的符号剥离，
目标程序仍使用 release 优化和 thin LTO；证据中记录 `build_profile=release`
及该覆盖。没有将 debug 运行记作 release 验收。

## 实测发现与修正

1. 每次 session 更新触发全局 NOTIFY，会令重连提交等待 PostgreSQL object
   lock。取消 session 更新的全局通知后，1,000 在线 / 100 活动档通过：心跳
   P99 383.93 ms，API P95 59.55 ms；仍保留新 owner 的本地唤醒和定时补偿。
2. 5,000 档暴露整批清除连接归属的锁扩散，以及大量重连耗尽已有设备的
   数据库连接。改为每批 64 条、SKIP LOCKED 的短提交，以及数据库初始化
   准入。两个回归分别在修复前失败、修复后通过。
3. 固定 4 个初始化名额时，5,000 档心跳 P99 824.53 ms、API P95 207.62 ms，
   API 无错误、无采样锁等待、服务端日志无错误；但仅 1,631 次重连在预算内
   完成，仍判失败。最终准入按连接池的一半分配并封顶 16；首个 hello 与 session 注册合并为一次提交，而非放宽测试门槛。
4. 连接唤醒原本会重复执行全局维护。将维护与 OTA 检查改为独立的每秒周期，
   且跳过错过的周期。实际行锁回归在修改前失败，修改后确认维护等待不阻塞
   其他 Build 的新任务调度。该修正改善 1,000 档，但没有单独解决 5,000 档的
   重连恢复问题；诊断显示连接 RPC 超时，继续分别记录初始化各阶段耗时。
5. 进一步诊断抓到 WAL 提交瓶颈：繁忙采样的 45 个活动查询中，44 个等待
   WALWrite / WalSync。幸存副本准入等待 P99 达 14 秒，连接初始化被挤压。
   将可覆盖的健康快照更新改为当前隐式事务内异步提交，降低逐台刷盘开销。
   新 session/归属、租约、命令和具体 OTA 升级事务保留数据库提交策略。
   真实 mTLS 回归通过数据库触发器观察提交设置，并检查全部池连接后续事务；
   修改前失败，修改后通过。数据库崩溃可丢失最近未刷盘的健康样本，后续心跳补齐。
6. 10,000 档的启动探测仍发现最多 15 个通知 object lock 等待，阻塞者多为
   COMMIT。所有工作触发器改为通过非阻塞事务 advisory lock 合并通知，
   未发送通知的事务仍提交 Outbox。回归持有通知协调锁，覆盖 job、节点、
   项目、attempt 和取消触发器，确认命令/取消可提交并由补偿投递，且释放锁
   后正常通知恢复；修改前失败，修改后通过。
7. 通知合并后 10,000 档可进入故障测试，但重连仍超出预算。旧设备表约
   25 万次更新中 HOT 次数为 0。用独立复制表、相同 10,000 行和随机种子
   对比 16,000 次单行更新：移除 `last_seen` 索引字段并采用 80% fillfactor 后，
   HOT 从 0/16,000 变为 16,000/16,000。随后相同 1,000 行的更新计划记录 WAL
   从 813,522 降至 119,630 字节。单行同步提交吞吐只从 778 增至 820 TPS，
   因此该局部基准只证明写放大下降，容量仍由完整故障压测判断。
8. HOT 优化后万台实测的 HOT 更新比例约 94%，但连接准入排队 P99 仍达
   14.55 秒，身份查询和会话更新分别需要数据库往返。登记改为一次有条件
   UPDATE，将 hello 中的节点 ID 与实际 mTLS 证书摘要、撤销、证书有效期
   一起核对后写入会话。真实 mTLS 回归固定了冒用另一个 ID、未知 ID、未登记
   证书、撤销和过期的拒绝行为，且拒绝后原有 session/owner 不变。
9. 合并登记后，万台心跳仍因额外授权读取占用连接池。普通健康更新已在
   UPDATE 条件中验证 session、撤销和有效期，健康确认改为复用该结果；
   活动租约与具体 OTA 事务继续独立核验。新增实际双副本 mTLS 回归，确认
   被替换的旧流不能写健康状态或获得确认，而当前流可确认，撤销和过期的
   流均关闭；同一回归在去除重复读取前后通过。
10. 空闲心跳减少为一次授权更新后，20 条连接档重连提高至 5,664/6,667，
    但仍超出预算，且心跳 P99 未达标。将 HA 的每进程预算设为 40，准入仍
    封顶 16，保留更多连接处理既有设备，并验证整体资源预算；没有放宽任何
    延迟、恢复、样本或原 attempt 保留门槛。
